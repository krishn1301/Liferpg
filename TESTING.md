# Testing LifeRPG on real hardware

The automated suite covers the arithmetic — streaks, XP, clean days, schedules,
the reminder plan, the daily-log averages. What it cannot cover is everything
behind `canRemind`, which is false in jsdom and in every browser. **Until a build
runs on a phone, none of the notification code has executed even once.**

This file is the list of things only a device can answer. Work down it after any
release that touches reminders, storage, or the shell.

## The rig

- **adb** is at `C:\Users\Admin\AppData\Local\Android\platform-tools\adb.exe` and
  is not on PATH — call it by full path.
- **Test phone:** Galaxy S9+ (SM-G965F), Android 10 / API 29, 1080×2220, giving a
  411×846 CSS viewport. USB only; wireless debugging needs Android 11+.
- **Screenshots:** `adb exec-out screencap -p > shot.png` **through a POSIX
  shell, not PowerShell.** PowerShell's redirect adds a BOM and text-encodes the
  stream, producing a corrupt PNG.
- **Always `adb install -r`.** Never uninstall: the phone holds real habit
  history and there is no sync to restore it from.

---

## 1. Updating (run this first, on every release)

The one check that catches an entire class of bug.

- [ ] Install the new APK over the previous one.
- [ ] **First launch shows the new version** — check Settings for the version
      string, and Today for whatever the release added.

- [ ] **The app is not stuck on a blank screen.** White rather than the app's
      black means nothing rendered at all.

If the first launch shows the *previous* build, a service worker is serving a
cached copy of an APK that is no longer on disk. This happened going 0.1.0 →
0.3.0 and is why native builds now ship a self-destroying worker
(`selfDestroying` in `vite.config.js`). A regression here means that broke.

If the first launch is **blank white**, the worker is in a reload loop: the
registration script re-registers a worker that unregisters itself and navigates,
forever. That is what v0.3.1 shipped, and it is why `injectRegister` is `null`
for native builds. It is invisible in every browser and every unit test — this
checklist item is the only thing that catches it.

## 2. Reminders

Nothing below has an automated equivalent.

- [ ] Set a reminder two minutes out. Lock the phone. It fires.
- [ ] **The status-bar icon is the three-block mark, not a white square.**
      `ic_stat_icon` is generated by `npm run icons`; Android keeps only its
      alpha channel and tints it, so an opaque icon renders as a solid blob.
- [ ] Tapping the notification opens the app.
- [ ] Tick the habit off before a later reminder — the rest of that habit's day
      goes silent.
- [ ] An "n times a week" habit stops nudging once the weekly target is met.
- [ ] A vow never produces a reminder. There is nothing to be nudged to do.
- [ ] Delete a habit that had reminders; nothing of its fires afterwards.
- [ ] Settings reports a plausible queued count, and it changes as habits are
      added and completed.

### Expect delay, not precision

Reminders are scheduled with `allowWhileIdle: false`. Android's Doze can hold a
notification until the next maintenance window, so a 7am reminder on a phone
that sat still overnight may land late. That is a deliberate trade: exact
delivery needs `SCHEDULE_EXACT_ALARM`, which Google Play restricts to apps that
genuinely need alarm precision, and a habit nudge does not.

**A two-minute test with the screen off does not prove overnight behaviour.**
The only real check is setting a reminder for tomorrow morning and leaving the
phone alone.

## 3. Permission

- [ ] Deny notifications, then confirm Settings says so plainly rather than
      claiming reminders are queued.
- [ ] Revoke permission in system settings while reminder times are saved —
      the times survive, and Settings reports the denied state.
- [ ] Grant permission from the Settings button; the queue fills.

### Not testable on this phone

**The Android 13+ runtime `POST_NOTIFICATIONS` prompt cannot be exercised on the
S9+.** It is API 33+; on API 29 notification permission is granted at install.
Anything that passes here says nothing about a tester on a newer phone, where a
permission gate appears that this device never shows. Record it as untested, not
as passed.

## 4. Durability

The desktop predecessor lost data; this is the check that it cannot happen here.

- [ ] Set a mood, energy and a note. `adb shell am force-stop com.liferpg.app`.
      Reopen — all three survived.
- [ ] Record a relapse, force-stop, reopen — the streak is still reset and the
      slip is still listed on the vow.
- [ ] Tick a habit, force-stop within a second (inside the save debounce),
      reopen — the completion survived.

## 5. Excel export

- [ ] Export from Settings. The share sheet appears and the file opens in a
      spreadsheet app with four sheets: Daily Habits, Statistics, Daily Log,
      Config.

## 6. iPhone PWA

Different engine, different rules — none of the Android results carry over.

- [ ] Share → Add to Home Screen. The icon is the LifeRPG mark, **not a
      screenshot of the page** (that is what happens when `apple-touch-icon`
      fails to resolve).
- [ ] Safe areas: the header clears the notch and the tab bar clears the home
      indicator.
- [ ] The date pickers in the relapse sheet and the vow editor are usable —
      Safari renders `input[type="date"]` quite differently from Chrome.
- [ ] The habit sheet's "Remind me" field shows the "needs the installed app"
      note rather than a control that would do nothing.
- [ ] After a deploy, the app picks up the new version on relaunch rather than
      staying on the old one indefinitely (`src/platform/updates.js`).

### Known and permanent

**Reminders cannot work in the iPhone PWA.** Safari has no scheduled local
notification API, and Web Push needs a server this app deliberately does not
have. The interface says so in words. This changes only when a native iOS target
exists — at which point `canRemind` turns true on its own, because it tests
"native or not" rather than naming a platform.
